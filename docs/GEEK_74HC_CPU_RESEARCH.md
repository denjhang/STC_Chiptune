两条路线对照:
| | 路线 A: STC32G MCU (stc2413, 进行中) | 路线 B: 74HC TTL CPU (本文档) |
|---|---|---|

**路线 B 不是为了性能** (TTL CPU 永远追不上 MCU), 是为了**"在完全自己懂的硬件上,

终极验证. 性能不够就降采样率, Lo-fi 本来就是芯片音乐的本味.

的 74HC-Chiptune 状态. **反馈回路健全 > 绝对性能**.

### chiptune 在 v1.5 上的可行性 (算力账)
- 22050Hz × 50 指令/采样 ≈ **1.1 Mips** → v1.5 (0.44) **不够**
- 8000Hz × 50 指令 ≈ 0.4 Mips → **勉强 (简单 PSG)**
- 4000Hz (Lo-fi) → 能跑更复杂

**v1.5 能做的**:
- ✅ 降采样率 (4-8kHz) 的简单 PSG (AY8910/SN76489 单/少通道)
- ✅ 节奏游戏型简单音效 (查表+包络)
- ❌ FM 合成 (算力差一个数量级)
- ❌ NES DMC/PCM (内存+算力都不够)

**结论**: v1.5 目标定为 **PSG chiptune (降采样率)**, 不碰 FM.
FM 留给将来 (升 v3 并做熟, 或 STC32G 整机路线成熟后, TTL CPU 作"原理验证").

## 8. v1.5 扩展口 = chiptune 的救星 (2026-06-26 关键发现)

### v3 砍扩展口 = 自断手脚 (用户原话: "笑了, 还是 v1.5 好")

v3 (Minimal-UART-Computer-3) **没有扩展 GPIO 口**, 只能 UART 串口输出.
v1.5 有扩展口, 配套 **GPIO Card** + **VGA Card** (含完整 KiCAD + 程序).

**对 chiptune 的致命影响**:
- v3 只能 UART 输出音频 → 高采样率时 CPU 大量时间耗在串口等待 → **性能强 2.5× 的 v3,
  在音频输出上反而不如 v1.5**
- v1.5 扩展口能外接 DAC → 并行输出 → 输出开销可忽略

### GPIO Card 揭示: 内存映射并行输出 (`STA 0xdff0`)

路径: `.../Revisions 1.3 - 1.6 (FLASH)/Expansions/GPIO Card/`

`gpiowrite.txt` 示例程序揭示 GPIO Card 的本质:
```asm
; control digital outputs of the GPIO Expansion Card
#org 0x8000
    LDI 0xfe STA 0xffff      ; 配置
loop:
    LDI 1   STA 0xdff0       ; 往内存映射地址写一字节 → GPIO 并行输出
    ...
```
- **`STA 0xdff0` = 内存映射 I/O** (不是串口), 速度 = 1 条 STA 指令 (几个时钟周期)
- **并行 8-bit 输出** (示例写 1/2/4/8 做 LED 跑马灯, 是 8 位并行口)
- 配套 `gpioread.txt` (读 GPIO) + VGA Card (VideoRAM, 完整 KiCAD)

### chiptune 音频输出方案: GPIO → R-2R DAC

```
STA 0xdff0  →  GPIO 8-bit 并行输出  →  外接 R-2R 梯形电阻 DAC  →  RC 低通 → 音频
```
- R-2R 电阻网络几毛钱, 或廉价 DAC 芯片 (TLC7226 等)
- **8-bit 输出, 和 STC32G 的 PWM DAC 同档次**, 音质够 chiptune
- 关键: **输出开销 = 1 条 STA**, CPU 几乎全用于合成

### 算力账重算 (GPIO 输出后)
原来担心 UART 是瓶颈, 现在 STA 直接写 DAC, 输出开销可忽略:
- v1.5 (0.44 Mips) @ 8kHz: 每采样 ~55 条指令预算
- → **够跑 AY8910 单通道 + 简单包络**
- @ 4kHz (Lo-fi): 预算翻倍, 能跑多通道 PSG

### 选 v1.5 的两条硬理由 (现在更充分)
1. **反馈回路健全**: 用户做过, 真机当诚实裁判 (stc2413 模式)
2. **GPIO 并行输出**: 扩展口外接 DAC, 音频开销可忽略; v3 砍了扩展口反而更差

## 9. v1.5 算力评估 + MY4TH 对比 (2026-06-26 硬算)

### 指令周期模型 (基于 v3 microcode_def.csv 真实微码)
v1.5/v3 指令集相同 (64 条), 微码可作参考. 每 T-state = 1 时钟周期.

加法类指令的真实 T-state 数 (从微码步数实测):
| 指令 | T-states | 微码步数 |
|---|---|---|
| ADI (A+=立即数) | 5 | 取指3 + 取立即数1 + 执行1 |
| ADA (A+=绝对地址) | 8 | 取指3 + 取操作数地址2 + 取操作数1 + 执行1 (估) |
| ADR (A+=寄存器间接) | 11 | 取指3 + 间接寻址多几步 + 执行 |

**校准** (作者给的数据点互相印证, 可信):
- v1.x: `1.0 Mips @ 8.3 MHz` → 平均 8.3 周期/指令
- v3: `1.1 Mips @ 8 MHz` → 平均 7.27 周期/指令

### v1.5 @ 3.6864 MHz 每秒加法次数

**峰值 (连续 ADI 不取操作数不存结果)**:
```
ADI = 5 T-states
每秒 ADI = 3,686,400 / 5 = 737,280 次/秒 ≈ 737K 次/秒
```

**实际 (带循环开销的保守估计)**:
```
典型加法循环: ADI(5T) + INC(5T) + BCC(5T) ≈ 15T/次
实际吞吐 = 3,686,400 / 15 ≈ 245,000 次/秒 ≈ 245K 次/秒
```

### 和 MY4TH 对比

| | v1.5 Minimal UART | MY4TH |
|---|---|---|
| 每秒 8 位加法 | **~245K (保守) / 737K (峰值)** | **6,300** |
| 差距 | — | **v1.5 是 MY4TH 的 ~40-117 倍** |

**完全不是一个数量级**. MY4TH 的 6300 次/秒意味着每加法 ~580 周期 (若同主频),
说明它要么主频极低 (几十 kHz), 要么每指令周期数极多 (多相时钟/单总线分时).
这种水平连 Pong 都吃力, 是"教学演示级".

v1.5 的 ~245K-737K 是 **C64/Apple II 同档** (作者宣称 2.3× C64, 校准属实):
- ✅ 能跑实时音频合成 (4-8kHz PSG, 每采样 50-180 条指令预算)
- ✅ 能跑图形游戏 (Pong/方块/曼德博集合, 已有程序证明)
- ✅ 能跑浮点 (README 说支持 32-bit 单精度)

### slu4 设计的高效之处 (为什么比 MY4TH 强这么多)
- **取指只占 3 周期** (`COL|MIL, COH|MIH, RO|II|CE|ME` — 16-bit 地址一次取完, PC 自增)
- **微码直接驱动控制信号** (不是多相时钟, 一个 T-state 干一件事)
- **ADI 只要 5 周期** (取指3 + 取立即数1 + 执行1)

MY4TH 这类极简教学 CPU 通常: 多相时钟 (一条指令几十相位) + 单总线分时复用 +
每指令 50-500+ 周期. slu4 在"74HC 能多高效"这点上做到了极致.

### 对 chiptune 的意义
v1.5 ~245K 加法/秒 + GPIO 并行输出 + R-2R DAC, 三件凑齐:
- 8kHz 下每采样 ~30 条指令预算 → AY8910 单通道 (查表+计数器+包络) 能跑
- 4kHz (Lo-fi) → 多通道 PSG 也行
- **MY4TH 那个 6300 连想都别想** (8kHz 下每采样 0.78 条指令, 算不完一个采样)

### 局限 (GLM 能补 — 语言工具开发是甜区)
- ❌ 无宏 (macro) — 大程序啰嗦
- ❌ 无条件汇编 (ifdef)
- ❌ 无通用表达式求值 (只能 `label±N`, 不能 `label+label`)
- ❌ `#include` 被注释掉 (可能 bug)
- ❌ 错误处理弱 (只有 "Undefined expression")

**这些全是 GLM 强项**: 给汇编器加宏/条件汇编/表达式求值/错误诊断,
是结构化、规则化的语言工具开发, 训练充分, 有 asm.py 这个干净基础可改.

### 输出格式
"cut & paste" 格式: 16 字节一行, `:xx xx ... xx`, 带 `#org` 地址头.
适合通过 UART 粘贴到 Minimal CPU 的原生编辑器/汇编器.
**但我可以加一个直接输出 .bin 的选项** (灌仿真器的 flash.bin).

### 和 min.py 的关系
- asm.py: 汇编器 (汇编 → 机器码)
- min.py (283 行): MIN 高级语言编译器 (Python-like → 机器码)
- **两者输出同一机器码格式**, 都 MIT 开源, 都 GLM 友好

**结论**: 软件工具链 (asm.py + min.py) 是本项目最坚实的资产 — 开源、可改、
GLM 强项. 比 74HC-Chiptune (iverilog/yosys, GLM 弱项) 强太多.

**74HC DIY CPU 里的怪物级别**.

### 12.3 贴片 vs 直插 (封装决定频率上限)

- **直插 (DIP) 封装**: 走线寄生电容大, **只能 8MHz**
- **贴片 (SMD) 封装**: 寄生电容小, **能上 50MHz**
- 这是**硬件物理限制**, 不是设计选择. 74HC 的引脚电感和走线电容在高频下是瓶颈.

**对 chiptune 的选型影响**:
- 贴片 50MHz (5.9 MIPS): 能跑多通道 FM (stc2413 级), 但焊接难度大 (SMD)
- 直插 8MHz (0.94 MIPS): PSG + 低采样率 FM 勉强, 焊接容易 (DIP)
- **性能差 6 倍**, 但贴片焊接门槛高. 用户已下单 (待确认是哪个版本).

### 12.6 GLM 三连错的教训 (评估萤火虫算力时犯的)

评估萤火虫算力时, GLM 连续三次严重错误, 根因都是**没锁定数据前提就反推**:

1. 第一次: 用 NES **0.1 FPS** (错误数字, 实际 3 FPS) 反推 → 0.2 MIPS
   - 用户纠正: "nes 那个你算错了, 他模拟 cpu 还模拟 gpu"
2. 第二次: 用 3D demo + **错误浮点假设** (假设软浮点 50-100 指令/次) 反推 → 0.4 MIPS
   - 实际 ALU 表存储器可能硬件辅助, 浮点没那么慢
3. 第三次: 把**贴片 50MHz 的 5.9M add/s 当成直插 8MHz 的** → 高估 6 倍
   - 用户纠正: "那些 add 测试都是贴片 50m 版本"

**教训 (写入, 给未来 GLM)**:
- **反推之前, 先锁定数据的精确条件** (哪个版本/什么主频/什么测量方法/含不含 I/O 开销)
- **实测一句话 > 读 200 行代码反推**. 用户的 `uchar add 5913600/s` 比所有架构分析都准.
- **不要用"74HC 一定慢"的刻板印象拒绝接受高数字**. 和 stc2413 "8051 跑不动 FM" 同陷阱.
- **"能跑 X" ≠ "能实时跑 X"**: NES 模拟器"能跑"但 3FPS (含 PPU), 3D demo"能跑" 15-25FPS.
  要问"跑多快", 不能只看"能不能跑".

## 13. 萤火虫直插 8MHz 能做什么 (能力清单, 2026-06-26)

> 基于反推的 0.94 MIPS (uchar add ~940K/s, 从贴片 50M/5.9M 线性缩放, **待真机验证**).

### ✅ 完全能做

**1. PSG chiptune (AY8910/SN76489/SCC)** — 萤火虫的主场
- PSG 本质: 频率计数器 + 音量查表 + 简单包络, 每通道 5-10 条/采样
- 3 通道混音 + 包络 ≈ 30-50 条/采样
- @22050Hz: 0.94M/22050 ≈ **每采样 42 条指令** → **能跑 3 通道 PSG @22050**
- @8000Hz: 预算翻 2.7 倍 → **能跑 6 通道 PSG + 噪声 + 包赠**
- 龙少吃豆子游戏已证明游戏音频这条路通

**2. 简单音效 / 节奏游戏音频**
- 鼓声 (查表 + oneshot 衰减, 像 stc2413 假噪声法)
- 8-bit 旋律 + 鼓点

**3. PC MIDI 播放 (若 VS1003 硬解)**
- VS1003 若接成硬件 MIDI 解码, 萤火虫只送命令不算合成 → MIDI 几乎免费
- **但失去"自己实现合成"的意义**, 到手后确认 VS1003 接法 (第一件事)

### ⚠️ 勉强能做

**4. 低采样率单通道 FM**
- stc2413 单 op FM ≈ 30-50 条/采样
- @8000Hz: 预算 117 条 → **能跑 2-3 通道简化 FM @8000Hz** (电话音质)
- @22050 只够 1 通道, 无意义
- 能体验 FM 原理, 但音质降级

**5. NES APU 部分模拟 (不含 DMC)**
- 2 方波 + 三角 + 噪声 ≈ 40 条/采样
- @22050 勉强, @11025 舒服
- DMC (PCM 流) 吃内存, 1MB 够放但算力紧

### ❌ 做不了 (硬上会卡死, 重蹈 stc2413 早期全量移植覆辙)

**6. stc2413 级 6 通道 FM + 5 鼓声 @22050**
- 需 ~3-5 MIPS (STC32G 30M+ 跑都偶尔卡), 0.94M 差 3-5 倍

**7. 高采样率多通道 PCM/ADPCM**
- 1MB RAM 够放, 但 0.94 MIPS 撑不起多通道实时混音

### 关键变量: VS1003 用法 (到手第一件事确认)

| VS1003 接法 | 萤火虫角色 | 影响 |
|---|---|---|
| 硬解 MIDI/MP3 | 只送命令 | MIDI 免费, 但失去学合成原理的意义 |
| 当 DAC (I2S/PWM) | 萤火虫算合成 | 和 stc2413 同模式, **推荐** (契合"完全掌握合成"目标) |

### 直插版定位总结

**直插萤火虫 = slu4 64x4 的"富工具链版"**:
- 碾压 slu4: LCC (C 直接写, 不碰汇编), 1MB RAM (放音色/波形), VS1003 (音频现成), 浮点库
- 不如 slu4: 无仿真器 (真机唯一裁判), Protel 非 KiCAD, 用户没做过 (slu4 v1.5 做过)
- **最佳定位: PSG chiptune 平台 + C 语言学习机**, 不指望 FM 多通道

价值不在快, 在**透明** — 从 74HC 到 ISA 到 LCC 到应用, 每层都看得见改得动懂得了.

## 14. 萤火虫指令集 + 与 STC 对比 (2026-06-26)

### 14.1 萤火虫是栈式字节码机器 (stack-based bytecode)

**证据**: GlowCompiler 的 `bytecode.cpp` line 140-165, 编译器后序遍历 AST 输出指令:

```c
case ADD: case SUB: case MUL: case DIV: case MOD:
case BOR: case BAND: case BXOR: case RSH: case LSH:
    dumptree(p->kids[0]);         // 先压左操作数入栈
    dumptree(p->kids[1]);         // 再压右操作数
    print("%s\n", opname(p->op)); // 出栈运算, 结果回压栈顶
```

**指令集特征** (代码 + 结构图综合):
- **栈机器**: 运算不指定寄存器, 操作数隐式从栈顶取 (像 Java JVM / Python 字节码)
- **指令类型齐全**: ADD/SUB/MUL/DIV/MOD (算术) + BAND/BOR/BXOR (位操作) +
  LSH/RSH (移位) + EQ/NE/GT/GE/LE/LT (比较跳转) + ASGN/CALL/RET/ARG/JUMP
- **256 字节寄存器堆** (结构图): 栈的辅助 (局部变量缓存), 非主运算寄存器
- **A/B 累加器 + IO0/IO1** (c.h 的 XOP 定义): I/O 和快速访问
- **为 C 设计**: 指令集天然匹配 C 语义, 这是 LCC 能移植的根本原因

### 14.2 三种指令集架构对比 (根本差异)

| | 萤火虫 | slu4 | STC8/STC32 |
|---|---|---|---|
| **风格** | **栈式** (操作数隐式在栈顶) | 寄存器式 (A/B 显式) | **累加器式** (8051 ISA) |
| 运算示例 | `PUSH a; PUSH b; ADD` | `LDA a; ADB b` | `MOV A,a; ADD A,b` |
| 类比 | Java JVM / Python | 6502 / Z80 | 8051 / 6502 |
| 指令密度 | 高 (不编码操作数位置) | 中 | 低 (8051 指令长) |
| C 编译器难度 | **最易** (栈机天然匹配 AST 后序遍历) | 中 | 难 (累加器要寄存器分配) |

### 14.3 为什么萤火虫能跑 LCC, slu4 只有 MIN

**栈机是 C 编译器最友好的目标**:
- C 表达式树 (AST) 的后序遍历 = 栈机指令序列 (左子树→右子树→运算)
- 不需要复杂的寄存器分配算法 (累加器机/寄存器机的难点)
- LCC 的 bytecode 后端几乎直接对应栈指令

这就是龙少能把 LCC 移植成功的根本原因 — **不是龙少更努力, 是栈架构天然适合编译**.
slu4 (寄存器式) 没有完整 C 编译器, 只有 MIN 脚本, 因为寄存器分配难写.

### 14.4 与 STC8/STC32 的算力对比 (真实数据)

STC32G144K246 跑 **72MHz HPLL** (main.c:20 `MAIN_Fosc = 72000000L`, 代码实证),
STC32G 是 32 位 1T 8051 (大部分指令单周期):

| CPU | 主频 | 架构 | MIPS | 是萤火虫直插的 |
|---|---|---|---|---|
| STC8H (8051, 48MHz, 1T) | 48MHz | 8 位 8051 | ~40 MIPS | **43×** |
| **STC32G144K246** (stc2413) | **72MHz** | 32 位 1T 8051 | **~60-70 MIPS** | **64-74×** |
| 萤火虫贴片 50MHz | 50MHz | 8 位栈机 | ~5.9 (实测) | 6.3× |
| **萤火虫直插 8MHz** (已下单) | **8MHz** | 8 位栈机 | **~0.94** (反推) | **1×** |
| slu4 v1.5 | 3.6864MHz | 8 位寄存器 | 0.44 | 0.47× |

**萤火虫直插 8MHz ≈ STC32G 的 1/70**, 差两个数量级.

### 14.5 STC 快但难学, 萤火虫慢但好懂 (根本权衡)

**STC32G 快的原因**:
- 32 位 (一次 4 字节, 萤火虫 1 字节; ulong add 实测只有 uchar 的 16%)
- 1T 8051 (大部分指令单周期, 72MHz ≈ 72 MIPS)
- 硬件乘除单元 (MUL/DIV 单周期)
- 但: 8051 指令集古老 (1980), 累加器瓶颈, 编译器要做复杂寄存器分配

**萤火虫慢的原因**:
- 8 位 (多字节运算线性变慢)
- 栈机每运算多次访存 (压栈/出栈), 指令多
- 无硬件乘除 (软件实现)
- 但: 栈指令集简单透明, **每条指令都看得懂**, C 编译器容易写

### 14.6 两个平台不是竞争, 是不同学习层次

| 平台 | 学什么 | 性能 | 适合 chiptune |
|---|---|---|---|
| **萤火虫直插** | 从 74HC→ISA→LCC→应用**全栈理解** (栈机/字节码/编译器后端) | 够 PSG | ✅ PSG 主场 |
| **STC32G** | **真实工程平台** (高效 C, ISR 优化, 标准音源兼容) | 够 FM 多通道 | ✅ stc2413 已完成 |

**对应长远目标 (0.0 节) 两条路线**:
- 路线 A (STC32G): 性能平台, 标准兼容 chiptune (stc2413 已完成)
- 路线 B (萤火虫): 原理平台, 理解整机从零怎么造

萤火虫直插 0.94 MIPS **够学原理、够做 PSG、够跑通"从 74HC 到 chiptune"全链路**.
它的价值不在快, 在**透明** — 每层都看得见、改得动、懂得了. STC32G 是黑盒 (芯片内部看不见),
但跑得快能做真东西. 两者互补, 不替代.

## 15. 萤火虫的 PC 通信机制 (2026-06-26, 关键工程约束)

> **核心结论: PC→萤火虫通信走 CH375 USB 主机 + 并行总线, 不是串口, 要自己开发协议.**
> 这和 slu4 (天生 UART) / stc2413 (USB CDC) 根本不同, 直接影响 chiptune 开发模式.

### 15.1 萤火虫没有原生 UART (关键发现)

slu4 的 CPU 微码有 `OUT`/`INP` 指令直接对接 UART 芯片, 一条指令收发.
**萤火虫自身没有 UART 外设**, 靠外挂芯片实现串口/USB:

| 外设 | 芯片 | 接法 | 用途 |
|---|---|---|---|
| 双串口 | SC16IS752 | **SPI→UART (软件位模拟 SPI)** | 串口通信 @115200 |
| USB 主机 | **CH375** | **8 位并行总线** | U 盘/键盘/鼠标 |
| ROM 烧录 | 专用下载器 | 独立小板 | 烧 FLASH (非运行时) |

### 15.2 CH375 = USB 主机 + 并行总线 (用户判断: "USB 转并口")

`ch375.h` 铁证:
```c
#define CH375_DATA  IO1              // 8 位并行数据走 IO1 端口
#define CH375_A0    M_IO0_DO3        // 地址/命令线
#define CH375_WR    M_IO0_DO7        // 写选通
#define CH375_RD    M_IO0_DO6        // 读选通
#define CH375_CS_0  M_CS3            // 片选

#define CH375_WR_DATAREG(device, data) \
    CH375_DATA = (data); \            // IO1 = 数据 (并行写)
    CH375_CS_A0_WR_LOW(device); \     // WR 拉低 (并口写时序)
    CH375_CS_A0_LOW(device);          // WR 拉高 (完成一次写)
```

- **CH375 是 USB 主机芯片** (不是 USB 转串口), 萤火虫是 USB host
- 通过 **IO1 (8 位并行数据) + IO0 (WR/RD/A0/CS 控制线)** 驱动 CH375
- CH375 再接 U 盘/键盘/鼠标 (NES 模拟器/吃豆子都用它)
- 时序是**并行总线握手** (CS→A0→WR→数据), 不是串口逐位

### 15.3 "要自己开发简单协议" (用户判断, 完全准确)

CH375 只提供 **USB 传输层** (端点收发 8 字节包, `CH375_WR_USB_DATA7` / `CH375_RD_USB_DATA0`),
**上层协议要自己定**:
- USB 枚举 (CH375 有底层命令, 但应用层要写)
- 文件传输 / 命令协议 (自己设计帧格式)
- FatFS 已有 (龙少移植), 但那是 U 盘文件系统, 不是 PC 通信

对比三种平台的协议开发成本:
| 平台 | PC→MCU 路径 | 协议开发 | 单字节开销 |
|---|---|---|---|
| **stc2413** | USB CDC (虚拟串口) | **零** (pyserial write) | ~1 指令 |
| **slu4** | 原生 UART | **零** (终端 paste) | 1 指令 (OUT/INP) |
| **萤火虫** | CH375 USB 主机 + 并口 | **要自己写** | ~5-10 指令 (CS/A0/WR/数据) |

### 15.4 chiptune 在萤火虫上的现实通信路线

既然 PC 实时通信成本高, 最务实的方案:

**方案 A: U 盘离线播放 (推荐, 复用现成驱动)**
- VGM 文件拷 U 盘
- 萤火虫 CH375 读 U 盘 (驱动龙少写好了, NES/吃豆子在用)
- FatFS 管理文件 (驱动也有)
- chiptune 程序: U 盘读 VGM → 合成 → VS1003 输出
- **完全自包含, 不依赖 PC**. 代价: 不能动态切曲/实时调试

**方案 B: SC16IS752 串口 monitor (调试用, 非正式播放)**
- 烧 ROM 时带小 monitor, 通过 SC16IS752 串口收调试命令
- SC16IS752 软件 SPI 慢, 但调试不在乎速度
- 用于开发期参数调整, 不用于播放

**不推荐: CH375 实时下发 VGM**
- 要写完整 USB 设备端协议栈 (PC 当 USB 设备), 太复杂
- 而且单字节开销 5-10 指令, 0.94 MIPS 下挤占音频算力

### 15.5 通信是萤火虫做 chiptune 的短板 (诚实结论)

萤火虫的强项是**自包含应用** (程序+数据全在 FLASH, LCD 显示, U 盘存文件),
**不是实时交互** (PC 动态下发). 设计哲学和 slu4/stc2413 不同:

| 设计哲学 | slu4 / stc2413 | 萤火虫 |
|---|---|---|
| 定位 | 终端交互的"播放器" | 自包含的"计算机" |
| PC 关系 | PC 实时灌数据 | PC 只用来烧 ROM / 拷 U 盘文件 |
| 通信 | 原生 (UART/USB CDC) | 外挂 (CH375/SC16IS752) |
| 适合 chiptune | ✅ 实时 VGM 播放器 | ⚠️ 离线 U 盘播放器 |

**就"PC 通信做实时 chiptune"这个具体场景, slu4 v1.5 (天生 UART + 用户做过)
可能比萤火虫更合适**. 萤火虫的优势 (LCC + 1MB + 算力 2×) 在"离线自包含 chiptune 播放器"
场景才发挥出来.

### 15.6 待到手确认的通信问题
1. ROM 下载器走什么接口? (USB 转 SPI? 转并口? 决定烧 ROM 流程)
2. CH375 是否能当 USB device 模式 (接 PC)? (若不能, PC 实时通信彻底走不通, 只能 U 盘)
3. SC16IS752 实测吞吐? (115200 软件位模拟, 实际有效速率可能远低于标称)

### 15.7 解决方案: FT232R/FT232H — USB 串口/并口桥接 (2026-06-26)

> **这是让萤火虫获得 stc2413 级别"PC 实时下发"能力的最务实方案** (用户提出).
> 用 FTDI 芯片当 USB→并口/串口桥梁, 把"自己开发协议"的成本降到最低.

#### 为什么 FT232 比 CH375 适合"PC→萤火虫"

核心差异: **方向反了**.

| | CH375 (萤火虫现有) | **FT232R/H** |
|---|---|---|
| USB 角色 | 萤火虫当 **主机** (PC 当设备) | **PC 当主机** (FT232 当设备) |
| PC 端开发 | 要写 USB 设备端程序 (复杂) | **pyserial/ftd2xx 直接 write (零开发)** |
| MCU 端协议 | USB 枚举 + 传输协议 (重) | 读并口引脚/串口字节 (**几乎零**) |
| 数据路径 | PC→USB设备协议→CH375→并口 | **PC→pyserial→FT232→并口引脚→萤火虫IO** |

**关键**: CH375 让萤火虫当 USB 主机, 反过来要 PC 当 USB 设备 (PC 端写设备端代码, 复杂).
FT232 让 **PC 当主机** (PC 本来就是), 萤火虫只读并口, **协议几乎为零**.
这正是"最基本的 usb 串口转并口程序"的含义 — PC 发字节, FT232 转并口电平, 萤火虫 IO 读.

#### FT232R vs FT232H 选型

**FT232R (便宜, 串口为主)**:
- 本质: USB 转串口 (UART) 芯片, 最常见的 "USB 转 TTL" 模块
- 并口能力: 只有 CBUS 几个引脚可配位模式 (不是真并口)
- 速率: UART ~3Mbps (够 VGM 命令流)
- 价格: ~10-15 元, 淘宝到处有
- 问题: 萤火虫无原生 UART, FT232R 的 TX/RX 还得接到 SC16IS752 或软件位模拟接收
- 适合: 简单场景, 或已有串口接收路径

**FT232H (贵, 真并口, 更适合萤火虫)**:
- 本质: USB 转多协议芯片 (FTDI 高性能版)
- **并口能力: 真 8 位并行 FIFO 模式** (或 bitbang 16 路 IO)
- 速率: 并口模式高达几 MB/s (远超 chiptune 需求)
- 价格: ~40-60 元 (模块, 如 Adafruit FT232H breakout)
- **适合萤火虫的原因**: 8 位并口**直接对接萤火虫 IO1** (都是 8 位并行),
  配合 RXF/TXE/RD/WR 握手信号
- 萤火虫端协议极简: 等RXF拉低→RD拉低→读IO1→RD拉高 (~5 条指令)

#### FT232H 接法 (理想, 待到手确认 IO0 空闲位)

```
PC (pyserial/ftd2xx 写字节)
   ↓ USB
FT232H 模块
   ↓ 8 位并口
   D0-D7  →  萤火虫 IO1 (8 位数据端口, 直接对接!)
   RXF#   →  萤火虫 IO0 某输入位 ("有数据"信号)
   RD#    →  萤火虫 IO0 某输出位 ("读选通")
   GND    →  共地
```

**PC 端** (和 stc2413 的 vgm_player 几乎一样):
```python
import ftd2xx   # 或 pyftdi
dev = ftd2xx.open(0)
dev.write(bytes([0x51, reg, data]))   # 复用 stc2413 的命令格式
```

**萤火虫端** (C 代码, 极简):
```c
while (RXF == 1);     // 等数据 (查 IO0 位)
RD = 0;               // 拉低读选通
byte = IO1;           // 读 8 位数据
RD = 1;               // 释放
// 处理 byte (按 stc2413 同样的命令协议)
```

**协议层几乎为零** (裸字节流), 上层协议 (VGM 命令格式) 可**直接复用 stc2413 的
0x51/0xB5 那套**. 这就是"最基本的程序" — 不需要 USB 枚举, 不需要文件系统,
就是 PC 写字节 → FT232H 转并口 → 萤火虫读 IO.

#### 四方案最终对比

| 方案 | PC 端 | 萤火虫端 | 协议开发 | 适合 |
|---|---|---|---|---|
| CH375 (现有) | 写 USB 设备端 | 写 USB 主机协议 | **重** | U 盘离线 |
| **FT232H** | **pyserial/ftd2xx** | **读 IO1+握手** | **几乎零** | **PC 实时 (像 stc2413)** |
| FT232R | pyserial | 接 SC16IS752 或软件串口 | 中 | 简单场景 |
| SC16IS752 (现有) | pyserial | 软件 SPI 读 | 中 | 调试用 |

**FT232H 是让萤火虫获得 stc2413 "PC 实时下发"能力的最佳桥梁**.
花 ~50 元买模块, 接几根线到 IO0/IO1, 就能像 stc2413 一样从 PC 实时灌 VGM.
比 CH375 方案 (写 USB 主机协议) 省太多事.

#### 待到手确认的接线问题 (FT232H)
1. IO0 高 3 位是片选 (CS0-CS7), 低 5 位是数据/控制 — **有没有空闲位给 RXF#/RD#?**
2. 若 IO0 被外设占满, 可能让 FT232H 占一个 CS 槽位 (如 CS6/CS7)
3. FT232H 的 3.3V/5V 电平是否匹配萤火虫 IO (确认后加电平转换若需要)

#### 对 chiptune 开发模式的影响

有了 FT232H, 萤火虫的 chiptune 开发能进入 **stc2413 模式**:
- PC 实时下发 VGM 命令 (像 vgm_player)
- 萤火虫实时合成 + 输出 (VS1003 当 DAC 或 PWM)
- 快速迭代: 改 PC 端参数 → 立即听效果 (不用重新烧 ROM)
- **通信开销 ~5 指令/字节, 0.94 MIPS 下可控** (VGM 命令流不密集, 间歇性)

这让萤火虫从"自包含 U 盘播放器"也能变成"PC 实时播放器", 开发效率大幅提升.
**买 FT232H 模块是萤火虫 chiptune 项目的推荐配件** (~50 元, 性价比极高).
