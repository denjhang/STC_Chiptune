# YM2413 (OPLL) FM 合成芯片集成进度 (2026-06-24 更新)

Yamaha YM2413 (OPLL) 是第八个集成进 STC32G144K 固件的音源芯片
(继 AY8910/SN76489/SCC/NES APU/GB DMG/NES FDS 之后).

总览状态见 `README.md`.

## 0.0 长远目标 (项目 north star, 2026-06-26 用户口述)

### 0.0.0 真实驱动力 (比任何宏大叙事都根本)

> "玩这么久芯片音乐却不了解合成原理, 不能自己设计音源, 这很没意思."

**"没意思"三个字才是项目真正的发动机.** 不是为了省钱/交付/KPI, 是**认知好奇心** —
"用了十年的东西, 我到底懂不懂它". 这种驱动力最持久, 不被外部挫折打断
(不像"为省钱"遇到更便宜方案会动摇).

**触发问题: "如果芯片库存耗尽, 我该怎么办?"**
- 收藏者姿态: 依赖实物, 芯片没了就没了, **被动**
- 本项目姿态: 掌握合成原理, 芯片没了能自己合成出来, **主动**
- 这个问题逼出根本区分: **是"会播芯片音乐", 还是"懂音频合成"?**
  前者依赖资产, 后者拥有能力. stc2413 选后者.

- **全部开源免费**

> "那可是几乎整个数字音频历史, 宝贵的技术资产, 免费给我."

**大多数人把 libvgm 当"播放器后端", 本项目把它当"音频合成原理的完整教材"** —

这彻底定义了 stc2413 的本质: **不是"劣化移植", 是"以 libvgm 为教材, 把数字音频

技术. 做完 8 个, 等于把数字音频史的主流合成技术全过了一遍.

### 0.0.3 音频是训练场, 不是终点

做完 8 个音源 (AY/SN/SCC/NES/GB/FDS/YM2413), 真正练出的是"**如何在资源约束下做
实时仿真/裁剪**"这套手艺. 每个音源都是一道约束习题:
- NES APU (DMC/PCM 流式) → 内存受限下的流式数据管理
- GB DMG → 算力受限下的通道裁剪
- YM2413 → 听感拟合 vs 算法复制的取舍

**这套手艺直接迁移到整体复古游戏机仿真** — 因为游戏机仿真本质是"CPU 指令解释 +
多芯片协同 + 内存映射 + 实时输出", 和音源仿真同构, 只是规模更大.
音频是相对简单的子系统, 借它把"约束仿真"方法论练透, 整机时手艺已在, 只是套用.

长远路径 (从小到大):
```
音源子系统 (当前: 8 音源完成, stc2413 是最难的 FM)
    ↓
单芯片整机 (如纯 AY 的机器)
    ↓
多芯片整机 (MSX = YM2413+AY, SMS, FC = NES APU)
```
ROM 是标准测试集 (和音源用 VGM 测试同一思路).

## 0.1 评估方法论 (必读, 给所有接手者, 包括未来的 AI)

**判断 stc2413 好不好的第一证据, 不是和 emu2413 的 dB 对照, 是曲库规模 —
`vgm/opll/` 下有 421 首 VGM, 覆盖 ys/sor/s1/msxfan/ysfm/ysms/90s 等 17 个子目录,
各种游戏类型和年代.**

这是用脚投票的结果: 听感不行不会堆到 421 首 (效果差到第 20 首就放弃了).
曲库规模证明的是"整体听感"这个维度 — 它是**涌现的, 无法被单点精度证伪**.
某个音色 RMS 偏 2dB、某鼓相似度 70%, 不影响整体听感站得住; 反之局部再精确,
整体不对也不会有人往里堆曲子.

**所以评估 stc2413 的优先顺序**:
1. **第一证据**: 曲库规模 (421 首, 整体听感用脚投票) ← 最硬
2. **第二证据**: 真实 YM2413 硬件听感对照 (用户 10 年+ 芯片经验 + 大量实物)
3. **第三证据**: 和 emu2413 的局部对照 (dB/RMS/波形) ← 只是参考, 不是标准

### 不要拿科学尺度量工程 (三个项目的定位)

很多人 (包括 AI) 的默认潜意识是"精度阶梯":
```
Nuked-OPLL (cycle-accurate, 最高) > emu2413 > stc2413 (劣化版)
```
**这个框架是错的.** 这三个是不同问题的解, 不在一条阶梯上, 谁也不是谁的标准:

| 项目 | 回答的问题 | 成功标准 | 性质 |
|---|---|---|---|
| Nuked-OPLL | 硅片每个时钟边沿在干什么? | 和逻辑分析仪逐 ns 对齐 | 科学 (精确建模) |
| emu2413 | YM2413 的算法输出什么样? | 听感接近 + PC 跑得动 | 参考实现 (移植) |
| AVR FM (子午线cc) | FM 在最低端 MCU 能不能响? | 响, 且像音乐 | 探索 (证明可行) |
| **stc2413** | **YM2413 VGM 能否在 8051 上忠实播放?** | **真芯片听感 + VGM 直接灌** | **工程 (硬约束下取舍)** |

**技术含量不在一条轴上**:
- Nuked/emu 的正确性靠逻辑分析仪/规格书 (客观, 可验证, 1 维: 更精确)
- stc2413 的正确性靠**耳朵 + 一抽屉真芯片** (主观但有实物参照, 多维: 每个决策都牺牲
  什么换什么, 错了没有"更精确"的退路, 只能重新想方向)

### 常见错误 (AI 尤其易犯, 见第 6/7 节详细记录)

1. **见 64 点波形表就说"精度不够"** — 不问"为什么是 64 点" (AVR 起点继承 + 8051 算力)
2. **见假噪声就说"LFSR 劣化"** — 不识固定波形×频率本质是 FM 合成 (见 12.3.2a)
3. **见 sus_hold 表就说"凑的常数"** — 不读 gen_sus_hold.py 不知道是 log2 逆向离散化
   (见 12.3.5)
4. **想"把精度提到 19-bit/1024 点会更像"** — 反了, YM2413 是 9-bit DAC 低端芯片,
   提精度 = 更像 emu 但更不像真芯片 (见 12.0.1)
5. **拿 emu 当标尺调鼓声** — 模型完全不同, emu 在鼓声上帮不上忙 (见 12.3)

**纪律**: 见代码先问"它在解决什么问题", 不要套"标准实现"框架.
先看曲库规模 (421 首), 再谈精度.

## 0.2 工程哲学: 性能优化 > 换更强硬件 (stc2413 的降维打击)

stc2413 不只是一段代码, 它是一套**嵌入式音频性能优化的方法论**. 这套方法论的核心
命题: **不优化性能, 只换更强硬件, 是死路**.

### 0.2.1 反面 A: "换高性能 MCU + 全量移植 GME" (彭渔露路线)

常见做法: 上 AT32F415 (~150MHz Cortex-M4) 这种高性能 MCU, 全量移植 GME
(Game Music Emu, PC 端模拟器库).

**为什么是死路**:
- GME 全量移植 = 抄 PC 算法到 MCU, 不做裁剪/拟合/流式
- **但大容量 PCM (NES DMC bank, FDS wav) 和十几通道 FM VGM, 本质是内存问题,
  不是算力问题** — 换更强 CPU 解决不了 SRAM 不够
- AT32F415 SRAM 通常 256~512KB, 一个大 PCM VGM 就吃光
- "笑死" 的点: 不优化性能, 以为换硬件就行, 结果换了硬件还是卡在内存上
- **换硬件只能解决算力轴, 解决不了内存轴; 而真正卡人的往往是内存轴**

### 0.2.2 反面 B: "上 FPGA + 开源 YM2413 核心" (吴歧路线)

另一个常见建议: FPGA 精确还原, 有开源 YM2413 core 可用.

**为什么是死路 (对本项目)**:
- YM2413 要 **4K+ LE**, 8 音源全塞 = **32K+ LE**
- 这个规模的 FPGA 核心板成本是 STC32G (几块钱) 的 **几十到上百倍**
- 只解决"精确还原", 没解决"低成本多音源播放器"这个**真正的工程目标**
- **用 FPGA 做 YM2413 = 用大炮打蚊子**, 精度溢出, 成本爆炸
- 而且精度高 ≠ 听感对 (见 12.0.1: emu 比 Nuked 精度低但听感不一定差)

### 0.2.3 stc2413 的降维打击: 重新定义解空间

stc2413 一颗 STC32G (几块钱, 8051 内核, 低端中的低端), 塞进 8 个音源
(AY/SN/SCC/NES/GB/FDS/YM2413 + 鼓声). 不是靠算力强, 是靠**每个音源都做了
针对性的性能优化和听感拟合**:

| 音源 | 开发难度 | 难点 | 优化手段 |
|---|---|---|---|
| AY8910 / SN76489 / SCC | 秒杀 (半小时内) | 纯查表 | 直接移植, 无复杂度 |
| GB DMG | 搞半天 | 性能裁剪 (4通道+噪声, 省 ISR) | 通道裁剪 |
| NES APU | 搞一天 | DMC 流式 + PCM bank | 流式下发 + ring buffer |
| **YM2413** | **3 天** | FM + 鼓声 + 包络拟合 | 见第 12 节全套 |

**这才是让 FPGA 和高性能 DSP "感到颤抖" 的原因**: 不是 stc2413 算力强,
而是它**证明了"不用那么强的硬件也能做到"**. 这是工程上最致命的降维 ——
别人在"更强的硬件"轴上卷 (AT32 → STM32H7 → FPGA), 你在"更聪明的取舍"轴上赢
(8051 + 听感拟合). 解空间被重新定义了, 他们的硬件优势变得无关紧要.

### 0.2.4 stc2413 填补的真空: 中低端 MCU 合成音频 (无同行)

本系列项目 (STC_Chiptune, 含 stc2413 等 8 音源) 的真正定位是**深挖中低端 MCU 的
合成音频能力**, 限定条件极苛刻, **没有任何同行做过**:

- **主频 < 100MHz** (排除 STM32F4/H7, AT32F415 等 150MHz+)
- **非 Cortex 架构** (8051/C251; 排除所有 ARM Cortex-M, 这是最狠的限制 —
  市面 99% 的 MCU 音频项目都是 Cortex)
- **无硬件 DSP 单元** (无 FPU/DSP 指令; 排除 Cortex-M4F/M7)
- **合成音频** (FM/波形表实时合成, 不是放 wav; 排除 SD 卡播放器)
- **多音源 + VGM 兼容** (AY/SN/SCC/NES/GB/FDS/YM2413, 标准 VGM 直接灌;
  排除单一芯片 MIDI 合成器)

**五条同时满足的, 目前没有第二个公开项目.** 大多数"低端 MCU 音乐"要么是放 wav,
要么是单一芯片 MIDI 玩具. stc2413 填的是"中低端非 Cortex MCU 上的多标准音源 VGM
播放器"这个真空.

### 0.2.5 子午线cc 项目的真相: 原语来源, 但不是同类

stc2413 的 FM 原语 (64 点表/单表ADSR/round-robin) 源自子午线cc工作室的 AVR 项目,
但**两者不是同类项目**, 子午线cc 是**短期玩具**, stc2413 是**长期标准播放器**:

**修改日期证据** (`Reference_Project/STC-MCU/extracted/`):
```
ArduinoUnoFMsynsynthesizer    2020-07-28   ← stc2413 的 FM 起点
wavetable_synthesis           2020-10-04   ← 波形内存音源 (stc2413 鼓声思路源头之一)
ATtiny85SynthModule           2020-11-11
AVR-PS-2keyboardTinyFMSynth   2021-01-31   ← 最后一个, 之后停更 5 年+
```
**半年内做 4 个项目然后彻底停更** — 典型的"探索完可行性就放下"的短期玩具轨迹.

**关键差异: 子午线cc 不兼容任何标准**:
- 4 个项目全是 **MIDI 键盘 / PS2 键盘合成器** (自弹自听的乐器, 不是播放器)
- **不解析 VGM**, 没有寄存器兼容层, 不解码 YM2413 默认音色表
- 音色靠 MIDI SysEx 或键盘现场调, 不是从标准文件来
- 所以它**永远只能是"会响的 FM 合成器玩具"**, 不能播 MSX/SMS 音乐

**"子午线本人都不知道他的小玩具能兼容 YM2413"**:
- 他的 `fmtone.h` 有 `WAVE_TBL_SIZE 64` + `envelope_cnt[16]`, 这些原语**确实能撑起
  YM2413 兼容**, 但他从未往这个方向走一步 (没加寄存器解析/VGM/鼓声/默认音色表)
- 是**stc2413 识别出这些原语的潜力, 并补齐整个兼容层** (寄存器解析 + 默认音色 +
  EG 语义 + 鼓声 + 包络拟合), 才让它从"玩具"变成"标准播放器"
- 原语 ≠ 实现, 就像"知道砖头能盖房"不等于"盖了房子"

### 0.2.6 性能依赖 = 硬件平台依赖 (工程哲学内核)

前面 (0.1.1-0.1.3) 说的是"换硬件是死路", 这里说透**为什么**:
**对性能依赖越重, 对厂家/硬件平台依赖就越重.**

| 路线 | 对性能依赖 | 对平台依赖 | 后果 |
|---|---|---|---|
| 全量 GME 移植 | 极重 (算力+内存) | 极重 (绑死 AT32/STM32H7) | 涨价/断货就完, 被厂家绑架 |
| FPGA 开源核心 | 极重 (LE) | 极重 (绑死特定 FPGA) | 核心板贵且稀缺, 被平台绑架 |
| **stc2413** | **极轻** (8051 @<100MHz) | **极轻** (STC32G 几块钱, 国产) | **自由, 硬件成可替换耗材** |

**深挖中低端 MCU 能力 = 减少对高性能平台的依赖**. 不只是省钱, 是**减少被单一
供应链锁死的风险**: AT32 涨价? STM32 缺货? FPGA 核心板停产? stc2413 换颗同样
几块钱的 STC32G 继续跑. **性能优化做到极致, 硬件就成了可替换的耗材.**

这也是为什么"主频<100MHz / 非 Cortex / 无 DSP"这三条限制是**有意为之的** —
不是没能力上高性能 MCU, 是**故意待在最难的约束里**, 逼出最大优化空间.
留在舒适区 (Cortex-M4+) 谁都能做, 留在 8051 做出 stc2413, 才是稀缺能力.

### 0.2.6a 真实动机与背景 (纠正"省钱"叙事)

> 上面 0.1.6 的"省钱/独立自主"是 AI 自行升华的宏大叙事, **不是用户的真实动机**.
> 真实动机朴实得多, 记录如下, 以正视听 (2026-06-26 用户口述):

**真实动机: "扩展硬件适应能力, 都玩一玩, 总有收获"**
- 不是为了省钱, 是想让音源方案能跑在不同平台上 (STC/STM32/FPGA 都试),
  而不是绑死一家
- 探索性的, 不是 KPI 驱动; "都玩玩"本身就是目的

**真实痛点 (2025-07 前, 无 vibe coding 时代)**:
- 找人开发, **"有人只会 stc, 有人只会 stm32, 有人只会 fpga"** —
  嵌入式开发高度人力依赖, 每个人视野锁死在自己那块芯片里

## 0. 背景: YM2413 是什么

YM2413 是雅马哈 1983 年的 **2-operator FM 合成芯片 (OPLL)**:
- 9 通道旋律 + 5 鼓 (rhythm mode)
- 每 operator: phase generator + envelope generator (AR/DR/SL/RR)
- 16 内置音色 + 1 用户音色
- AM/PM LFO (颤音/震音)
- 用于 MSX, Sega Master System, ColecoVision 等

**和 FDS 的区别**: FDS 是频率调制 (查表+加法), YM2413 是**真正的雅马哈式 FM**
(sin 相位调制). 但本实现用**极简线性 FM** 替代, 不做 dB 域 log/exp.

## 1. 为什么不能直接移植 emu2413.c

libvgm 的 `emu2413.c` (1629 行) 完整移植到 C251 后:
- **卡死** — 18 operator × 60+ mul/sample 在 ISR 里太慢, 主循环饿死
- **tll_table[128][64][4] = 128KB** — 远超 xdata 64KB
- 需要 rate converter (sinc/blackman/浮点) — C251 不支持

**结论**: 必须用极简 FM 核心.

## 2. 极简 FM 方案 (参考 STC32G12K128 fm.c)

**核心设计** (参考项目 `STC32G12K128/fm.c`):
- **64 点 s8 波形表** (-31..31), 不是 1024 点 log 域
- **线性 FM**: OP1 输出直接加到 OP2 的相位索引 (`idx += ch_out`)
- **ADSR 查表**: `ym_env_cnt[16]` 速度表, round-robin 每 16 tick 更新一个通道
- **跳过静音通道**: `if (!key_on && env==0) continue`

**寄存器兼容** (关键): 完整 YM2413 寄存器解析, 解码后映射到极简参数:
- `0x00-0x07`: 用户音色 → mod_ml/car_ml/TL/FB/AR/DR/SL/RR/EG/WS
- `0x10-0x18`: f-number 低 8 位
- `0x20-0x28`: fnum-hi/block/sus/key-on
- `0x30-0x38`: instrument/volume
- `0x0E`: rhythm mode + drum key-on

## 3. 实现细节

### 3.1 音高计算 (精确, 8.8 定点)

writeReg 时算 **u16 8.8 定点** step, render 里只做加法:
```
step = fnum × 2^blk × YM_STEP_CONST × ml / 2   (结果 u16)
YM_STEP_CONST = 3579545 × 64 × 256 / (72 × 262144 × 22050)
render: pos = (pos + step) & 0xFFFF; idx = (pos >> 8) & 0x3F   (8.8, 一个周期=64×256=16384)
ISR: 22050Hz
```

**实测音高高一个八度**: blk 减 1 修正 (频率 ÷2). 不能动 step (会导致节奏错乱).

> ⚠️ **2026-06-25 勘误**: 本节旧版误写"u32 16.16 定点 / ×65536 / pos>>16",
> 实际下位机 (ym2413.c:122-123,237,577) 是 **u16 8.8 定点 / ×256 / pos>>8**.
> 这个错误描述曾导致 fw_real_sim.py 用错定点格式, 频率高 2.255× (见第 9 节).

### 3.2 ADSR 行为对齐 YM2413 (2026-06-24 修正)

**EG 语义** (对齐 emu2413 get_parameter_rate, 之前版本写反了):
| 行为 | YM2413 规格 | 极简实现 |
|------|------------|----------|
| Sustain (**EG=1**) | **保持 SL** (sustaining) | step=0 → env_tick 不降 |
| Sustain (**EG=0**) | **继续降到 0** (non-sustaining) | step=rel → 继续减 level |
| Release (sus=1) | 固定速率 5 | env_step=ym_rr_tab[5] |
| Release (sus=0) | 速率 RR | env_step=rel |
| Attack (AR=0) | 不启动 | env_state=0 |
| Attack (AR≥7) | 瞬间到顶 | atk≤2 → level=31 直接 decay |

**AR/DR/RR 三张表** (commit 93f7cb6, 替换旧 ym_env_cnt 单表):
- `ym_ar_tab[16]` = `[0,116,58,29,14,7,4,2,1,1,1,1,1,1,1,1]`
- `ym_dr_tab[16]` = `[0,255,255,175,88,44,22,11,6,3,1,1,1,1,1,1]`
- `ym_rr_tab[16]` = `[0,255,255,255,170,85,42,21,11,5,3,1,1,1,1,1]`
- 反推自 emu2413 attack/decay/release 全程时间 (round-robin 16采样/tick)

**env_tick 加法计数器** (commit 1f45584):
- 旧: `cnt >= step ? cnt -= step : cnt=250+走包络` (减法, reset 250 有累积误差)
- 新: `cnt < step ? cnt++ : cnt=0+走包络` (加法, step 真正代表周期)

**key_on env_cnt=0** (commit 1f45584): 消除 attack 启动延迟 (旧值 250 导致延迟 4000 采样).

**car.tl 映射** (commit 93bc777): `tl = vol>>1` (之前 `31-vol>>1` 写反, 导致最大音量时输出极小).

**sus_flag 只影响 carrier** (对齐 emu2413 set_sus_flag line 672:
modulator 的 type&1==0, sus_flag 永远不设).

### 3.5 鼓声方案 (单 op 简化路径, commit 7ff3348)

鼓声用独立 YM_DRUM 结构 (单 op), 不走 2-op FM, 开销约为旋律一半。
oneshot: 边沿触发 (reg 0x0E bit 0→1), 每采样 tick 包络, 衰减完自动清除。

| 鼓声 | 波形 | 频率 | env_step | 衰减时间 | 状态 |
|------|------|------|----------|---------|------|
| BD | sin | 100Hz | 16 | ~10ms | ⚠️ 音量/长度待调 |
| TOM | sin | 214Hz (ml=5) | 16 | ~10ms | ⚠️ 待调 |
| SD | noise | 25Hz | 28 | ~20ms | ⚠️ 单op (真2op听感好但卡ISR) |
| HH | noise | 755Hz | 46 | ~29ms | ✅ 正常 |
| CYM | noise | 755Hz | 255 | ~150ms | ✅ 正常 |

- 噪声表: `ym_noise[64]` (64 点假随机 ±31)
- 边沿触发: `ym_prev_drum_bits` 检测 reg 0x0E bit 0→1
- 渲染: `ym_render_drum(idx)`, 单 op 查表×level, 无 FM 调制
- 旋律只渲染 ch0-5 (6通道), 为鼓声腾 ISR 余量

## 6. 被证伪的假设

1. ❌ "完整 emu2413.c 能直接移植到 C251" — 错, 128KB tll_table + ISR 太慢
2. ❌ "step /2 能降八度" — 错, 破坏节奏. 用 blk-1 才对
3. ❌ "sus_flag 同时影响 mod 和 car" — 错, 只影响 carrier (type&1 判断)
4. ❌ "stc2413 鼓声 == emu 鼓声模型" — **错** (2026-06-26). stc2413 鼓声是 5 个独立
   单 op oneshot, 无 FM 调制无 LFSR 无 short_noise. BD 本是真二运算器被简化成查表.
   调鼓声不能拿 emu 当标尺, 见第 12.3 节.
5. ❌ "鼓声连起来是调参能解决的 bug" — **错** (2026-06-26). 根因是 oneshot 架构
   vs naruto 续命技法的根本冲突. 影响极少数曲子, 主流曲库不受影响, 见第 12.4 节.
6. ❌ "把步进改 19-bit / 波形改 1024 点会更像真芯片" — **错得最离谱** (2026-06-26).
   项目初期多次想照抄 emu2413 的 19-bit 相位 / 1024 点波形, 这是"精度焦虑"发作.
   **真相**: YM2413 是雅马哈最低端 FM 芯片, 9-bit DAC 阶梯效应严重, 真实硬件音质
   "其实很差" (中低音量有嘶嘶音). emu2413 没模拟 DAC 劣化, 反而比真芯片"干净"
   (美化失真). stc2413 的低精度 (64 点/8.8 定点/32 级包络) **方向上恰好贴近真硬件**,
   提精度 = 更像 emu 但更不像真芯片. 见 12.0.1.
7. ❌ "不用 LFSR 是因为不会 / 偷懒" — **错** (2026-06-26). ay8910.c 就用 LFSR,
   stc2413 的 ay8910 实现也有. 不用 LFSR 做鼓声是因为 **2-op FM 运算才是 CPU 瓶颈**,
   6 旋律已是当前主频极限, 鼓声走完整 2-op 直接爆 ISR. 要突破需 PLL 超频, 不是算法问题.
   见 12.0.2.

## 7. 教训

1. **极简不是偷工, 是换实现方式**. 64 点 s8 线性 FM 能达到"音色大体接近",
   不需要完整的 dB 域 log/exp 运算. 参考 12k128 fm.c 的设计.
   **注 (2026-06-26): 极简 FM 的真正起点是子午线cc工作室的 AVR 项目 (见 12.0),
   不是凭空设计的.**

2. **音高修正要改源头 (blk), 不是改结果 (step)**. step 同时影响相位和节奏,
   改 step 会连锁破坏节奏.

3. **寄存器兼容是底线**. FM 核心可以极简, 但寄存器解析必须 100% 兼容,
   否则 VGM 文件无法正确播放.

4. **PC 仿真必须和下位机 1:1 同步** (2026-06-24 教训).
   早期 fw_real_sim.py 没同步下位机的 env_tick/key_on/EG 逻辑, 导致 PC 验证
   结果不可信, 反复试错浪费大量时间. 改下位机任何东西, 仿真必须同步改.

5. **"只改表"包括数值 bug** (2026-06-24 教训). EG 语义写反、car.tl 映射写反、
   env_cnt 初始值荒谬, 这些都是"改数值"能修的, 不要因为"只改表"就不碰.
   但 round-robin/env_tick 逻辑/输出公式/波形/相位 这些是架构, 不能动.

6. **不要在 PC 上用 emu 精度假装验证下位机** (2026-06-24 教训).
   之前的 render_fm_v3/render_fm_v3_fw 偷用了 emu 的 ±127 波形/19-bit 相位/
   LEVEL_GAIN 查表/LFO, 生成的 WAV 和 emu 当然几乎相同, 但对下位机毫无意义.
   真正的验证必须用 render_fw_real (忠实下位机限制).

7. **6 通道 FM + 独立鼓声是性能极限, 不是设计选择** (2026-06-26).
   ch0-5 只渲染 6 通道是 STC32G 在 22050Hz ISR 下的算力天花板, ch6-8 让给鼓声.
   再多通道就卡死. 这和 AVR 起点 (也是 6 通道) 一致.

8. **鼓声 (尤其 HH/CYM) 是 stc2413 的原创贡献** (2026-06-26).
   AVR FM 起点没有鼓声. 用波形内存音源思路 (固定噪声表 + oneshot 衰减) 绕开 emu
   的 LFSR + short_noise 相位切换复杂度, 实机听感"非常好". 详见 12.3.

9. **低精度是还原硬件本貌, 不是缺陷** (2026-06-26 最重要的认知反转).
   YM2413 是雅马哈最低端 FM 芯片, 9-bit DAC 阶梯严重, 真实音质"其实很差" (用户 10 年+
   芯片经验 + 大量实物确认). emu2413 没模拟 DAC 劣化, 反而比真芯片"干净" (美化失真).
   **stc2413 的 64 点/8.8 定点/32 级包络, 方向上恰好贴近真硬件低精度面貌**.
   评价基准是**真实芯片听感**, 不是 emu 算法正确性. 提精度 = 更像 emu 但更不像真芯片.
   项目初期 19-bit/1024 点改造 (commit 873a3a5 → 无声) 就是这个错误思维的代价.

10. **2-op FM 运算才是 CPU 瓶颈, 不是 LFSR** (2026-06-26).
    ay8910 就用 LFSR (stc2413 的 ay8910 实现也有). 鼓声不用 LFSR 不是因为不会,
    是因为完整 2-op 运算 (BD 真调制 + HH/CYM/SD 的 to_linear) 在 6 旋律已是极限的
    情况下直接爆 ISR. 要加 ch6-8 / 真 2-op 鼓声 / LFSR 鼓声, 路径是 **PLL 超频**,
    不是改算法. 见 12.0.2.

## 9. 2026-06-25 音色准确度调试 (harpsichord 过反馈)

### 9.1 触发: harpsichord 听感"过反馈音质差"

用户反馈 inst 11 (Harpsichord) 过反馈导致音质差, 要求对照 emu2413 对齐.
**正确流程**: 先 PC 仿真 (fw_real_sim.py) 对照 emu2413 → 定位偏差 → 只改表/参数
→ 同步仿真验证 → 再改下位机.

### 9.2 发现1: fw_real_sim.py 一直没和下位机同步 (万恶之源!)

这是本次最重大发现, **颠覆了之前所有仿真结论**:

| | 仿真器 (修复前) | 下位机 (ym2413.c 实际) |
|---|---|---|
| 定点 | 16.16 (注释写的) | **8.8** |
| pos 类型 | u32 (`&0xFFFFFFFF`) | **u16** |
| idx 取法 | `pos>>16 & 0x3F` | **`pos>>8 & 0x3F`** |
| step 常数 | `×65536` | **`×256`** |
| 渲染采样率 | `INTERNAL_RATE=49716` | **22050** |

**后果**: 仿真器频率 = 下位机 × (49716/22050) = **2.255×**
- harpsichord 440Hz: 仿真器输出 **992Hz** (听感高八度+2半音), 下位机实际 **438.7Hz** (正确!)
- 用户听感"高八度+2半音"直接定位, 比所有数值分析都快
- **之前关于"过反馈""halfsin"的扫描结论全部建立在错误频率上, 不可信**

**修复** (commit 16839d4, 仅 fw_real_sim.py):
```
FW_STEP_CONST: ×65536 → ×256
FW_ISR_RATE = 22050 (新增)
fw_calc_step: 返回 & 0xFFFF (u16)
fw_render_fm: pos & 0xFFFF, idx = pos>>8 (8.8)
render_fw_real: 用 FW_ISR_RATE 而非 INTERNAL_RATE
save_fw_wav: 新增, 按 22050 保存 (save_wav 假设 49716 会错)
```
**验证**: harpsichord 440Hz → 仿真器 **441.0Hz**, emu 440.0Hz, 比例 **1.002** ✓

### 9.3 发现2: halfsin 负半周镜像 vs 静音

AGENTS.md 和本文档 3.4 旧版都记录 "halfsin 负半周镜像 (取绝对值)", 当成下位机
真实限制. **对照 emu2413.c:383-387 发现是 bug**:
- emu: halfsin 后半周 = `0xfff` (静音)
- 下位机: halfsin 后半周 = 镜像正值 (全正)
- **影响**: carrier 用 halfsin (car_ws=1) 时, 后半周本该静音却输出正值 →
  直流偏置 + 谐波污染 → 听起来像"过反馈失真"

仿真修复: `FW_HALFSIN` 后半周改 0. **下位机 ym_halfsin 表待同步** (ym2413.c:28-33).

### 9.4 发现3: volume 映射 bug (仿真器)

fw_real_sim.py 旧版 `car.tl = volume>>1`, volume=0 → tl=0 → 输出恒为0 (静音).
对照下位机 ym2413.c:500-502: `vol=(15-reg_vol)<<2; car.tl=vol>>1`.
修复: `car.tl = (60-volume)>>1` (volume 语义对齐 emu: 0=最大音量).

### 9.5 被否决的方案: mod.tl 映射翻转

试过把 `mod.tl = 31-(tl_raw>>1)` 改成 `tl_raw>>1` (让 TL=3 时 mod 衰减增大).
反馈占周期从 25%→1.6% 接近 emu 1.2%, **但听感音高变了** (FM 边带偏移).
**否决**: 影响所有乐器的 mod 衰减特性, 不是纯调参, 改动过大.

## 11. 教训 (2026-06-25 补充)

7. **文档描述必须和代码一致**. 旧 3.1 节写"16.16 定点"但代码是 8.8, 这个文档 bug
   传导到仿真器, 让所有调参白做. **改代码时同步改文档, 读文档时对照代码核实**.

8. **听感比数值分析快且准**. 用户听出"高八度+2半音"秒级定位频率 bug,
   而我做了 5 轮仿真扫描 (反馈/halfsin/mod.tl) 都没发现, 因为假设仿真器是对的.
   **仿真器本身不可信时, 数值结论全是假的**.

9. **"先修仿真器同步"是第一优先级**. 任何调参前必须确认仿真器 1:1 下位机,
   否则就是"在错误的地图上找路". 频率/定点格式/采样率是最容易不同步的地方.

10. **不要拿 emu2413 当标尺苛责 8051 实现** (2026-06-26 认知校准).
    emu2413 跑在 PC 上, 单采样单 slot 就要 1 次 1024 项 `exp_table` 查表 + dB 移位,
    6 通道 × 2 op = 12 次/采样, 光这个就吃光 22050Hz ISR 预算. KL/RKS/tll_table
    (128KB) / 19-bit 相位 / LFO 在 C251 上要么爆 xdata 要么爆算力.
    **所以 stc2413 缺这些不是缺陷, 是 8051 限制下的必然取舍.**
    正确的评价基准是: **主流 MSX/SMS 曲库听感** (99% 使用场景),
    而不是"每个细节都对齐 emu2413 算法". 实测主流曲库几乎完美, HH/CYM 还原尤其好.

11. **鼓声连不起来是架构特性, 不是 bug** (2026-06-26 定性, 见第 12 节).
    naruto 等少数作曲家用高速反复 keyon BD/SD "续命" 拉长鼓声, 这是 OPLL 驱动特有
    的特殊技法. stc2413 鼓声是 oneshot 单 op 衰减计数器, 架构上不支持"续命",
    已做的 trigger 续命 (level>0 只重置 env_cnt) 是 oneshot 模拟状态机的天花板.
    **调参 (方案 A/B) 能改善但无法根治**, 因为根因是架构 (oneshot vs 真 EG 状态机).

## 12. stc2413 评估基准 + 鼓声架构定性 (2026-06-26)

### 12.0 真正的起点: 子午线cc工作室的 AVR FM 项目 (不是凭空造的)

stc2413 **不是从零造的**, 也不是 emu2413 的移植. 真正的技术起点是**子午线cc工作室

### 12.0.1 为什么"极简/劣化"不是缺陷, 反而是还原硬件本貌 (最重要的认知)

**这个认知颠覆了项目早期反复出现的"精度焦虑"**. 项目初期多次想把:
- 步进改成 19-bit (照抄 emu2413 的 `DP_WIDTH = 2^19`)
- 波形精度改成 1024 点 (照抄 emu2413 的 `fullsin_table`)

这些都被证明是**搞笑的过度工程**, 根本原因不只是"跑不动", 而是 **目标本身就错了**:

**YM2413 是雅马哈最低端的 FM 芯片, 音质本来就很差**:
- 内置 **9-bit DAC**, 阶梯效应严重 (输出右移 quantization 噪声大)
- 中低音量区有特有的 **"嘶嘶"音** (用户 10 年+ 芯片音乐经验 + 大量真实 YM2413 硬件
  实测确认)
- 在现代听感标准下, YM2413 真实硬件音质"其实很差"

**emu2413 (libvgm) 没有忠实体现这一点** — 它是算法级仿真, 追求 FM 运算的正确性,
但**没有模拟 9-bit DAC 的阶梯量化噪声和嘶嘶音**. 所以 emu2413 听起来反而比真芯片
"干净", 是一种**美化过的失真**.

**精度最高的仿真 Nuked-OPLL** (`Reference_Project/furnace-master/extern/Nuked-OPLL/`)
是 cycle-accurate 逐时钟边沿模拟 (连 `rm_hh_bit2/3/7/8` 硬件相位抽头都精确还原),
比 emu2413 准确得多. 它的输出处理 (`opll.c:1024` `ch_out = output>>3`, 区分
`opll_type_ds1001` 高品质 DAC vs 真实 YM2413) 才更接近真实硬件的低精度面貌.

**所以 stc2413 的"极简/劣化缩水"反而是对的**:
- 64 点 s8 波形 + 8.8 定点 + 线性 FM + 32 级包络 — 这些"低精度"特性,
  **方向上恰好和 YM2413 真实硬件的 9-bit DAC / 低精度运算一致**
- 不追求 emu2413 那种"算法正确但音质过干净", 而是接受甚至利用"劣化"来贴近真芯片听感
- **这是"硬件本来的面貌", 不是偷工减料**

**教训 (给后续调参)**: 不要再产生"把精度提高会更像 emu/更像真芯片"的想法.
- 提精度 = 更像 emu2413 (美化版), 但**更不像真实 YM2413 硬件**
- 评价基准是 **真实芯片听感** (用户有大量实物对照), 不是 emu 算法正确性
- 项目早期 commit 873a3a5 的 19-bit/1024 点改造 → 无声, 就是这个错误思维的代价

### 12.0.2 为什么不用 LFSR (虽然 ay8910 就用了) — 6 通道是 CPU 极限

LFSR 本身不贵 (ay8910.c 就用 17-bit LFSR 做噪声, stc2413 的 ay8910.c 也实现了).
但 YM2413 鼓声用 LFSR 不是孤立的 — 它要配合 **完整 2-op 运算** (BD 是真二运算器,
HH/SD/CYM 的噪声要进 `to_linear` 1024 项查表).

**真正的 CPU 瓶颈不是 LFSR, 是 2-op FM 运算**:
- stc2413 当前渲染 6 旋律通道 (ch0-5) 已经是 **STC32G 当前主频的极限**
- 6 通道同发偶尔卡死 (ISR 性能瓶颈, 见第 5 节)
- 鼓声如果也走完整 2-op (像 emu 那样 BD=真调制 + HH/CYM/SD 走 to_linear),
  相当于再多 3-7 个通道, **直接爆 ISR**
- 所以鼓声用单 op oneshot + 固定噪声表 (见 12.3), 完全绕开 2-op 运算

**同一问题的另一面: MSX 的 YM2413+AY 组合也卡死 (git 证据)**:
- MSX 标准配置是 **YM2413 (FM 旋律+鼓) + AY8910 (SSG 噪声)** 双芯片
- 下位机同时跑 YM2413 的 6 通道 FM + AY 的噪声通道 → ISR 爆
- **解决**: vgm_player.py 加 `--ym2413` 参数 (YM2413-only 模式), 上位机直接 strip 掉
  其他芯片命令 (SN/AY/GB/NES/SAA/SCC), 只发 YM2413 + wait
- git: `29a73f8` 首次加入 (commit message 原话: **"下位机算力不足, 只能单芯片"**),
  `26f4e37` 改成显式 `--ym2413` 参数 (避免误伤其他芯片 VGM),
  `5820f19` 提示改简洁 `skip:chip1,chip2`
- **这证明**: 不只是鼓声不能用 LFSR, **连 AY 的噪声都不能和 YM2413 并存**.
  6 通道 FM 已经吃满 ISR, 任何额外芯片/通道都卡死.

**要突破 6 通道限制的路径**: **PLL 超频实验** (待做, 不是改算法能解决的).
- 当前主频下, 6 旋律 + 单 op 鼓声已是天花板
- 想加 ch6-8 旋律渲染 / 真 2-op 鼓声 / LFSR 鼓声 / AY 组合, 都需要先超频提算力
- 这是硬件层面的下一步, 不是固件调参能解决的

### 12.1 stc2413 不是 emu2413 的劣化版, 是 8051 上的工程优化实现

逐项算账, 为什么不能直接移植 emu2413 (单采样开销):

| emu2413 操作 | 开销 | 在 stc2413 上的处理 |
|---|---|---|
| `to_linear` = 1024 项 `exp_table` 查表 + dB 移位 | 重, ×2 op ×6 ch = 12 次/采样 | 替代为 `(wave×(level+1)×(tl+1))>>10` 一次乘两次移位 |
| `calc_envelope` 19-bit `eg_counter` + `eg_step_tables` 多级查表 | 中, ×9 slot | round-robin 每 16 采样 tick 一个 op |
| `fullsin_table` 1024 项 dB→linear 曲线 | 中 | 64 点 s8 裸正弦 |
| `calc_phase` 19-bit 累加 + `pm_table` | 中 | 8.8 定点 u16 |
| `tll_table[128][64][4]` = 128KB KL 三维查表 | 重, 爆 xdata 64KB | **整个砍掉 (KL 没实现)** |
| `rks_table` 影响 `rate_h` (Key Rate Scaling) | 中 | **整个砍掉 (RKS 没实现)** |
| LFO (PM/AM) 每采样推进 | 中 | `#if 0` 关着 (性能不足) |

**结论**: emu2413 移植了就跑不动 (commit 873a3a5 用生命验证过). stc2413 用
"借 YM2413 寄存器接口 + 参数解码 + EG 语义直觉, 内核完全重写为线性查表 FM".

### 12.2 正确评价: 仿真度 90%, 低性能 MCU 上第一个 FM 兼容核心

| 评价维度 | 状态 |
|---|---|
| YM2413 仿真度 | **~90%** (用户实测判断, 主流 MSX/SMS 曲库听感) |
| 19 个默认音色在主流曲库 | ✅ 几乎完美 (实机验证) |
| HH/CYM 噪声类鼓声还原 | ✅ 非常好 (**原创, 见 12.3**) |
| 6 旋律 + 5 鼓声在 22050Hz ISR 跑得动 | ✅ (6 通道是性能极限) |
| 寄存器完整兼容 (VGM 直接灌) | ✅ |
| KL/RKS/LFO/相位精度对齐 emu | ❌ 但对主流曲库听感影响小, 合理取舍 |

**两个事实判断 (用户)**:
1. **仿真度 90%** — 不是"形似神不全", 而是实机听感的真实评价.
2. **这是实际上在低性能 MCU 上跑起来的第一个 YM2413 FM 兼容核心**.
   AVR FM (子午线cc) 是通用 FM 合成器, 不带 YM2413 寄存器兼容;
   stc2413 是第一个让 VGM 能直接灌进低端 MCU 播放的实现.

**之前误判 "还原 90% 是假的" 的修正**: 那是拿 PC 上的 emu2413 当标尺的纸上谈兵.
在 8051 约束 + 主流曲库基准下, 90% 是实机可验证的真实水平.

### 12.3 鼓声是真正原创的部分, HH/CYM 尤其精妙

鼓声是 stc2413 **区别于 AVR FM 起点的真正原创贡献** (AVR FM 项目没有鼓声).
设计思路: **用波形内存音源 (wavetable) 的方式做鼓声**, 极简但有效.

#### 12.3.1 emu2413 鼓声: "光打鼓都不够性能" (读 libvgm emu2413.c 真源码后算账)

emu2413 rhythm mode 一个采样 (`update_output`, emu2413.c:1012-1071) 要做:

1. `update_ampm` — AM/PM LFO 相位推进
2. `update_short_noise` (line 767) — 取 HH + CYM 两个 slot 的 `pg_out`, 抽 5 个 bit
   做 3 次异或, 算出 `short_noise` 标志
3. `update_slots` — 6 个 rhythm slot (BD mod+car / HH / SD / TOM / CYM) **全部** 跑
   `calc_envelope` (19-bit eg_counter + eg_step_tables 多级查表) + `calc_phase`
   (19-bit 相位累加 + pm_table 查表)
4. **每个鼓声都调 `to_linear` = 1024 项 `exp_table` 查表 + dB 移位**:
   - `calc_slot_hat` (line 996): short_noise + noise bit 选 4 个固定相位之一 → `to_linear`
   - `calc_slot_cym` (line 988): short_noise 选 2 个相位 → `to_linear`
   - `calc_slot_snare` (line 975): pg_out 高位 + noise bit 选 4 相位 → `to_linear`
   - BD: 真 `calc_slot_car(calc_slot_mod())` 二运算器 → 2 次 `to_linear`
5. `update_noise(14)` (BD 后) + `update_noise(2)` ×2 — 17-bit LFSR 共 18 次/采样

**性能账**: 光 HH/CYM/SD 三个 = 3 次 1024 项大表查表 + short_noise 异或 + 18 次 LFSR
+ 6 slot 的 19-bit 相位/包络. 在 8051 @22050Hz ISR 里, **一次 `to_linear` 就不可承受**,
emu 鼓声一个采样要 3+ 次. 这就是"光打鼓都不够性能"的字面含义 — 还没算旋律 ch1-6.

**结论**: emu 鼓声算法在 STC32G 上**根本不可能跑**. 必须自己造一套.

#### 12.3.2 stc2413 鼓声: 波形内存音源思路, 原理完全不同但效果逼近

stc2413 鼓声 (`ym_render_drum`, ym2413.c:642-666) 做同样的事只要:
- 一个 64 点伪随机噪声表 (`ym_noise[64]`, code 区, 零开销)
- `out = (wave×(level+1)×vol)>>6` — **一次乘两次移位**, 零大表查表
- oneshot 衰减计数器 (每采样 tick, 不走 round-robin)
- **没有状态机, 没有 LFSR, 没有 short_noise, 没有 to_linear**

#### 12.3.2a 假噪声表的双重身份: 低频=白噪声, 高频=共振峰 (核心合成洞见)

`ym_noise[64]` 名字带"noise", 但它**不是白噪声, 是一个固定的 64 点周期波形**
(和 `ym_sin[64]` 本质一样, 只是长得"乱"). 同一个表, step (读表速率) 不同, 行为完全不同:

**低 step (0-100Hz) — 逼近真 LFSR 白噪声**:
- 一个周期 = 64 点 × 256 (8.8 定点) = 16384, 走得慢, 周期 >10ms
- 人耳听不出 64 点的周期性 → 听起来就是"乱" = 噪声
- **行为上十分接近真 LFSR** (ay8910/sn76489 那种宽频噪声)
- **SD 用 25Hz**: 当白噪声用 (低频噪声 + 衰减)

**高 step (334-755Hz) — 变成有音高的金属共振峰**:
- 周期变短 (~1.3ms @ 755Hz), 周期性开始显现 → "有音高的怪波形"
- 叠加 755Hz step 本质是 **FM/环形调制合成 (频率 × 频率)**:
  假噪声表的频谱形状 × 755Hz 循环速率 = 金属镲片的共振峰
- 这不是"劣化版噪声", 是 **超简化的共振峰合成器**
- **HH/CYM 用 334-755Hz**: 当共振峰合成用

**这就是为什么 CYM 扫频要 5Hz 步进精扫 700-777Hz** (见 12.3.3 wav_drum_test5) —
不是找"噪声要多快", 是调**"金属共振峰在哪个频率"**. 镲片的金属共鸣就是这个频段的
频谱峰, 用"固定怪波形 × 755Hz 循环"拟合出来了.

**对比 emu 的本质区别**:
```
emu CYM   = 正弦 × (LFSR选相位) × to_linear   ← 算法复制硬件 (物理建模)
stc CYM   = 噪声波形 × 755Hz 循环 × 衰减      ← 频率×频率 拟合共振峰 (感知建模)
```
emu 在模拟"硬件怎么产生镲片声", stc2413 在直接合成"镲片声听起来什么样".
后者往往更高效 — 一个 64 点表 + 一个 step, 替代了 emu 的 LFSR + short_noise +
to_linear 一整套. 这是 stc2413 鼓声最精妙的设计, 也是"创造新东西"的核心.
(注: 项目初期提出 64 点假噪声方案时, AI 不信 — 没意识到固定波形×频率本质是 FM 合成)

**原理和 emu 完全不同, 但效果逼近 (用户实测相似度)**:
| 鼓声 | 相似度 | 说明 |
|---|---|---|
| **HH** | **95%+** | 噪声表 + 755Hz 扫频定频 + 快衰减, 几乎听不出和 emu 差距 |
| **CYM** | **95%+** | 同 HH 思路, 慢衰减 (~360ms), 金属镲片味逼近 emu |
| BD / TOM | 较高 | 单 op sin (emu 是真2op+to_linear, 这里简化但听感像) |
| **SD** | 偷懒 | 用户自评"偷懒的噪音" — 试过真2op/双包络/精确ADSR 都因卡ISR放弃, 单op noise 妥协 |

**为什么原理不同效果却能逼近**: 镲片/踩镲声的听感主要由 **高频噪声的频谱重心 +
衰减形态** 决定, 不由"噪声是真 17-bit LFSR 还是固定 64 点表"决定. 通过扫频扫到
噪声步进 755Hz (听感最像金属), 扫到衰减 ~360ms (听感最像镲片余振), 就能在听感空间
拟合 emu. **emu 在算法空间复制硬件 (LFSR + short_noise + to_linear + 真包络状态机),
stc2413 在听感空间拟合听感 (固定噪声表 + 扫频定频 + oneshot 衰减)** — 后者在 8051 上
是唯一可行解, 也是真正的"创造新东西", 不是移植.

这是 stc2413 区别于 AVR FM 起点 (无鼓声) 和 emu2413 (算法复制) 的**真正原创贡献**.

#### 12.3.3 鼓声频率/参数是逐个扫频实验出来的 (近 200 个 wav 实物)

下位机鼓声的固有频率和衰减参数 **全部是穷举式扫频试听确定的**, 不是拍脑袋.
全套实验在 `tools/wav_20250624/` (近 200 个 wav), 完整记录了"扫频→选频→定衰减
→对照emu→定型"的全过程:

**CYM/HH 固有频率扫描 (核心证据, 定到 755Hz 不是猜的)**:
- `wav_drum_test3`: hh/cym × {25, 50, 100, 200} Hz — 低频段粗扫
- `wav_drum_test4`: hh/cym × {1000, 2000, 5000} Hz — 高频段探
- `wav_drum_test5`: cym × {100, 200, 25, 50, 700, **725, 750, 755, 760**, 777, 1111} Hz
  — **在 700-777Hz 段 5Hz 步进精扫**, 最终锁定 **755Hz** (即 drum_fw_sim.py 的
  `NOISE_STEP_Q16 = int(755 * 64 * 65536 / INTERNAL_RATE)`)
- 结论: CYM/HH 金属镲片味在噪声步进 ~755Hz 时最像 emu, 是听感扫出来的
- 注: 下位机最终用 334Hz (ym2413.c:496 step=0x00F8), 755 是仿真侧扫描过程值

**BD 频率 + 单op/2op 对比** (`wav_drum_bd`, 15 个):
- bd / bd2op(真2op) / bdorig × {90, 100, 110, 120, 130} Hz — 定到 100Hz

**SD 是"偷懒的噪音" (用户原话), 但试过完整方案才妥协** (91 个实验):
- `wav_drum_sd` (63): sd_2env_n25~50 (双包络) / sd_exact_k20~500 (精确ADSR) /
  sd_fm_n30 / sd_fm_s5~6 (真2op FM) — 都试过, 听感好但卡 ISR
- `wav_drum_sd_fb` (8): fb0~fb7 全扫 (反馈量)
- `wav_drum_sd_s7` (20): sd_s7_n15~1000 (噪声幅度扫描)
- 最终: 单 op noise 25Hz 妥协 (真2op听感最好但 7 通道卡 ISR)

**衰减形态扫描** (`wav_drum_test`): cym/hh × {simple, fast, mid, slow} — 定衰减速度

**emu vs fw 对照** (每阶段都存 A/B): `wav_drum_adsr/` `wav_drum_complete/`
`wav_drum_final/` `wav_drums_emu/` vs `wav_drums_fw/` — 每个鼓都有 emu 参考和
fw 成品逐项对照.

**相关脚本**: `tools/drum_fw_sim.py` (DRUM_PARAMS 固化试听结果),
`tools/gen_sus_hold.py` / `gen_sus_decay.py` (衰减曲线生成).

**所以文档里的鼓声频率/参数是"听感空间拟合"的实验沉淀, 不是算法推导**.
改它们必须重新试听, 不能凭数值分析. 这是 stc2413 鼓声"原理完全不同但效果逼近"
的根基 — emu 在算法空间复制硬件, stc2413 在听感空间拟合听感.

#### 12.3.4 各鼓声设计 (init 参数, ym2413.c:494-498)
| 鼓声 | 波形 | 频率 | vol | env_step | 思路 |
|---|---|---|---|---|---|
| BD | sin | 100Hz | 16 | 14 | 低频正弦短脉冲 (emu 是真2op+to_linear, 这里简化成单op sin) |
| TOM | sin | 214Hz | 8 | 14 | 比 BD 高的鼓, 同 sin 思路 |

| **CYM** | **noise** | 334Hz | 2 | 255 | **噪声表长衰减 (~360ms), 原创, 效果好** |
| SD | noise | 25Hz | 8 | 28 | 低频噪声 (真2op听感更好但卡ISR, 单op妥协) |

**调鼓声时的纪律**: PC 仿真验证应对比 **stc2413 自己的鼓声衰减曲线 vs 曲子的
trigger 间隔**, **不要拿 emu 鼓声当标尺** — 模型完全不一样, stc2413 鼓声是自己的
原创设计, emu 在这里帮不上忙.

### 12.3.5 旋律包络拟合: 线性表伪装成对数形态 (声音"多像"的真正决定因素)

**核心命题**: 包络行为的相似性, 决定了声音到底多像. 这比波形精度/相位精度重要得多.
而 stc2413 (全线性) 和 emu2413 (全对数) 在包络域是**根本不同的两个世界**,
拟合它是整个项目最精妙的工程之一.

#### 12.3.5.1 emu2413 的对数世界 (读 libvgm emu2413.c 真源码)

emu2413 **整个是对数域 (dB 域) 运算**, 三张表互相配合:
- `fullsin_table` (line 172): `-log2(sin) × 256` — **波形存对数幅度**, sin 峰值→0,
  过零→2137 (最大衰减). 不是线性 sin.
- `exp_table` (line 153): `exp2(x/256) × 1024` — 把对数域**转回线性**用于输出
- `eg_out` (0~127): 包络也是**对数域**, 每 +1 = -0.375dB 衰减

**精髓在 `to_linear` (line 934-940)**:
```c
att = min(EG_MUTE, (eg_out + tll + am)) << 4;   // 波形dB + 包络dB + TL_dB + AM_dB
return lookup_exp_table(h + att);                // 对数域相加, 一次 exp 转线性
```
**对数域相加 = 线性域相乘**. 所以 emu 包络是 dB 域线性递增 (`eg_out += step`) →
输出是**指数衰减** (前期慢后期也慢, 自然听感, 和真实声学衰减一致).

#### 12.3.5.2 stc2413 的线性世界 + 形态鸿沟

stc2413 **全是线性**:
- 波形表 `ym_sin[64]` 存**线性值** (-31~31 裸正弦, 不是 dB)
- 包络 `level` 是**线性** (0~31)
- 输出 `(wave × (level+1) × (tl+1)) >> 10` — **线性相乘**

**形态鸿沟**: 若 level 线性递减 (`level--`), 输出是**线性衰减** (前期匀速, level 小时
迅速归零, 听感"突兀消失"). emu 是指数衰减. **纯改速度 (cnt) 永远拟合不了** —
扫描 sus_cnt=5~30 全证明过 (要么前期太快要么后期死掉, 见 YM2413_HANDOFF.md).

#### 12.3.5.3 拟合方案: 查表伪造指数形态 (不把 stc 改成对数)

**关键**: 没有把 stc 改成对数 (log/exp 运算 8051 跑不动), 而是用**查表 + 计数器,
在线性 level 序列上伪造指数衰减形态**.

机制 (`ym_sus_hold[32]` + `env_tick` case 3, ym2413.c:430-440):
```c
u16 thr = (ym_sus_hold[op->level] * op->sus_scale_x16) >> 4;  // 该 level 该停多久
if (op->sus_cnt >= thr) { op->sus_cnt = 0; op->level--; }     // 到了才降一级
```
**level 数值仍是线性的 (0~31), 但 level 递减的速率是非线性的** —
高 level (响) 停留久 (慢降), 低 level (轻) 停留短 (快降),
输出曲线就逼近了指数衰减形态.

#### 12.3.5.4 数学原理: 对指数曲线的逆向离散化 (gen_sus_hold.py)

sus_hold 表不是试听凑的, 是**数学推导出来的** (`tools/gen_sus_hold.py:31`):
```python
hold_ms = TAU_MS * math.log2(n/(n-1))   # level n 降到 n-1 该停留的时间
```
- emu 在对数域线性递减 → 输出 `2^(-t/tau)`
- 要让线性 level 匹配: `level(t) = 31 × 2^(-t/tau)`
- level 从 n 降到 n-1 的时间 = `tau × log2(n/(n-1))`
- log2(n/(n-1)): 高 n 时大 (停留久), 低 n 时小 (停留短)

这是**对指数衰减曲线的逆向离散化** — 把连续指数曲线重采样到 32 个线性台阶,
每台阶宽度反比于该处衰减速率. 数学上完全等价, 但:
- **PC 上算好 log2, 存成整数表** (`ym_sus_hold[32]`)
- **下位机只查表 + 整数比较, 零 log/exp 运算**

#### 12.3.5.5 攻击/释音也用同样思路

| 阶段 | emu (对数域) | stc2413 (线性表伪装) |
|---|---|---|
| Attack | `eg_out -= (eg_out>>s)+1` (对数域指数趋零) | `level += (31-level)>>2 + 1` (镜像指数, 低level大步/高level小步) |
| Decay | eg_out += step (dB线性) | level-- 线性 (实测 DR 查表让 Piano 太慢, 回退线性) |
| **Sustain** | eg_out += step (dB线性→指数输出) | **sus_hold[32] 查表** (高level慢/低level快, 伪指数) |
| **Release** | eg_out += step | **rel_hold[32] 查表** (sus_hold/10, 快10倍) |
| Volume | tll 对数域 | **ym_vol_tab[62] 对数查表** (等dB间距) |

**结果**: attack/sustain/release/volume 四个阶段都用"查表伪装对数"对齐了 emu,
只有 decay 退回线性 (查表反而让某些乐器太慢). 这就是 stc2413 听感"90%像"的根基 —
**不是波形像, 不是相位像, 是包络形态像**.

#### 12.3.5.6 已知硬限制: 32 级 + 线性表的代价

- **release 尾巴台阶**: level=1→0 是 -27.9dB→-99dB 硬跳变 (32 级无法表达 -30~-99dB
  精细衰减), 听感音尾突然消失. emu 的 128 级 eg_out 能平滑. **调 rel_hold 无效,
  数据证明** (扫描 div 5~30 都卡 -27.9).
- **sus_hold 单一 tau 多乐器共用**: 各乐器 RR/SL/EG 不同, 衰减时间常数不同,
  可能需要按 RR 缩放 (已部分实现 sus_scale_x16[16], 但仍粗糙).
- 这是"线性表 + 32 级"的固有代价, 要根治需提精度 (但见 12.0.1: 提精度反而更不像真芯片).

### 12.4 鼓声连不起来: oneshot 架构 vs naruto 续命技法 (根本冲突)

**背景**: naruto 等极少数作曲家用高速反复 keyon BD/SD 来"续命"拉长鼓声
(BB3/B-FIGHT). 这是 OPLL 驱动特有的特殊用法, 绝大多数 MSX/SMS 音乐不用.

**为什么连不起来 (架构根因)**:
- emu2413 鼓声用真 EG 状态机: keyon → DAMP → ATTACK, 能反复重启包络 → 能续命
- stc2413 鼓声是 oneshot 单 op 衰减计数器: trigger 一次 level 从 31 线性减到 0
- BD env_step=14 → 衰减 ~20ms, 而 BB3 vol 变化间隔 ~37ms → vol 变化时 level 已=0
- 已做的 trigger 续命 (level>0 只重置 env_cnt 不重置 level) 是 oneshot 模拟状态机
  的**天花板**, 无法真正重启包络

**方案定性**:
- 方案 A (持续振荡): 让鼓声 active 时不因 level=0 停止, vol=0 静音 vol>0 恢复.
  本质是用 oneshot 架构模拟状态机行为, 方向正确但和真 OPLL 行为仍有差距.
- 方案 B (延长衰减): 增大 env_step 让鼓声活过 trigger 间隔. 治标, 改了所有曲子的
  鼓声长度.
- 方案 C (PC 仿真): 先在 drum_fw_sim.py 复现"连不起来"确认根因. **应对比
  stc2413 自己的衰减曲线, 不是 emu.**

**现实判断**: 这是 oneshot 架构的固有硬伤, 影响的只是 naruto 类极少数曲子.
主流曲库不受影响. 调参能改善但无法根治, 除非未来重写鼓声为真状态机 (吃 ISR).
